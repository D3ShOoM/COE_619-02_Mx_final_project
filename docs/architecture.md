# Architecture Notes

This demo implements a Django version of the campus shuttle prototype.

## Data flow

1. A GNSS source, simulator, or test script sends positions to `/api/ingest/gps/`.
2. The backend snaps noisy points to the seeded route when the point is near the route.
3. `PositionPing` records are stored and the `Bus` last-known state is updated.
4. Occupancy counts are sent to `/api/ingest/occupancy/` or generated by the simulator.
5. The rider map polls `/api/vehicles/` and `/api/gtfs-rt/trip-updates/`.
6. The dashboard polls `/api/feed-health/`, `/api/vehicles/`, and `/api/logs/`.

## Backend components

- `Route`, `Stop`, `RouteShapePoint`: GTFS-static-style pilot route data.
- `Bus`: latest vehicle state for quick UI/API access.
- `PositionPing`: time-series position history.
- `OccupancyReading`: aggregate occupancy history.
- `SegmentStat`: travel-time profile per segment between stops.
- `FeedEvent`: simple system log.

## ETA model

The demo estimates ETA by measuring forward distance along the route and summing segment travel times. Segment profiles are represented in `SegmentStat`. `shuttle/services/eta.py` includes a scalar Kalman smoother for updating segment travel time as real observations become available.

## Privacy-by-design choices

- No camera, audio, BLE identity, Wi-Fi MAC, or personal device data.
- Occupancy is stored only as aggregate count and Low/Medium/High level.
- The API exposes vehicle telemetry and aggregate occupancy, not rider identity.
